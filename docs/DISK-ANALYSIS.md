# Disk Analysis (0.2.0)

## Boundaries and data flow

`DiskAnalysisPage` owns an `IStorageScanner`, one immutable `StorageAnalysisSnapshot`, background queries and cancellable background treemap layouts. `StandardStorageScanner` enumerates directory metadata with `FileSystemEnumerable`; it does not open every file, read content, hash files or persist a scan in SQLite. Unlike the review scanner, it includes readable system/temporary entries. Reparse targets are never followed, including a directory that changes to a junction after discovery. Access failures are counted, with at most 100 diagnostic samples; warnings and cancellation propagate incomplete flags through ancestors.

Nodes retain parent IDs and names instead of duplicating complete paths. Compact adjacency arrays support direct children; full paths are reconstructed on demand. Traversal and reverse aggregation are iterative, with checked 64-bit logical totals. Immutable snapshots separate analysis from live catalog state. This is an observation across time, not an atomic filesystem snapshot: files can change during enumeration. Refresh explicitly to replace it.

`TreemapLayoutEngine` computes hierarchical squarified rectangles using separate filtered weights. A 64-DIP spatial grid indexes hit tests. `StorageTreemap` uses one native GPU-backed Win2D CanvasControl, no WebView or control per file. Rendering is bounded to 12,000 rectangles, with at most 4,000 child slots per subdivision; excess children become a proportional aggregate. Very small descendants remain represented. Aggregates can be explored through the list and filters. Zero-byte entries remain listed but have no positive map area. Six unfiltered layouts are cached by folder and DIP dimensions; resize and filtering cancel obsolete work and reject stale results.

The folder tree lazily materializes the largest 250 directories per branch. All direct children remain accessible in the list, in pages of 200. Filtering lists matching descendant files. Percentages always use the current folder's **unfiltered logical total**; extension statistics explicitly refer to the scan root. Size and percentage have the same sort order with that denominator. Allocated-size sorting is unavailable because allocation is unknown. The splitter and expanded-map command adjust available space; narrow windows hide optional panes. Native list/tree controls provide keyboard access equivalent to canvas selection; the canvas has an accessibility description. Existing theme resources provide light/dark surfaces; category colors retain readable white labels.

## Catalog and management

Scanning/navigation/filtering have no catalog write path. `RegisterAnalysisEntryAsync` runs only after the explicit **Etiketle** action, validates the selected item and upserts that item alone. It does not add a Source or import descendants. Folder catalog Size remains zero: recursive analysis bytes never replace catalog semantics. Existing folder tags can be read despite changed directory timestamps. File tags use the existing revision identity. The shared TagDialog supports tag addition/removal; previews use the existing FilePreview with explicit modal lifetime management. Library's folder context action forwards its path to the cached analysis page.

Only one selected non-system, non-reparse, online file with a readable native ID can be recycled. Confirmation defaults to cancel, then metadata, ancestry, containment and native identity are rechecked through the existing deletion service. Directory/mass/permanent deletion is unavailable in this page. Cancellation or recycling triggers no silent permanent fallback. Successful recycling rescans the current root. An audit-write failure after recycling is reported separately from deletion failure.

Native identity is captured lazily at selection and checked again before the operation. Enumeration does not capture per-file IDs, so an identical replacement **before selection** cannot be proved different from scan-time metadata. Filesystem operations also retain a small check-to-shell-operation race; do not interpret validation as transactional isolation. Hard-link paths contribute logical bytes independently. Sparse lengths are logical lengths. Physical allocation and recoverable space are deliberately unknown; drive capacity/used/free are shown separately.

Modal previews use a fresh FilePreview with `ReleaseOnUnload=false`: ContentDialog can transiently unload its content during opening. The owning page explicitly awaits `ReleaseAsync` in `finally` on close and before leaving, so a temporary visual-tree transition cannot cancel the preview while streams still close deterministically. Other preview hosts keep their existing automatic unload release.

## Verification

Run `dotnet build CleanTag.sln -c Release -p:Platform=x64` and `dotnet run --project Tests/CleanTag.Tests.csproj -c Release`. The suite covers existing review/catalog/watcher behavior plus analysis totals, Unicode, dots, temporary/zero files, empty/missing roots, deep trees, cancellation before and during enumeration, real denied ACLs, junction loops, hard links, 5-GB sparse lengths, stale/renamed/replaced files, explicit registration isolation, deterministic proportional nonoverlapping geometry, hit testing, repeated navigation/filtering and a one-million-entry synthetic snapshot with bounded rendering and aggregate totals.

`dotnet run --project Tests/CleanTag.Tests.csproj -c Release -- --storage-benchmark` creates and removes its own 100/4,000/20,000-file fixtures (40 folders, 128-byte files). It records enumeration, aggregation, total, layout, existing review scanner baseline, active cancellation status/latency and cumulative process peak working set to ignored `work/storage-benchmark.json`. Cancellation is triggered synchronously after the first file observation, using a zero progress interval for that measurement only; the UI keeps the default 150-ms throttle. The benchmark uses warm local filesystem caches, is a single sample per size, includes process/JIT overhead and is not a drive-wide speed guarantee. The hierarchy/safety work means this scanner can be slower than flat review enumeration. A million-node layout test is a scale/correctness test, not a measured million-file disk scan. Windows 11 was exercised locally; oldest supported Windows 10 and mixed-DPI hardware still require separate validation.

## Optional NTFS acceleration

No NTFS-specific fast scanner is enabled. A standard scanner is useful across folders, mounted volumes and readable non-NTFS/network locations without elevation. Win2D adds a native immediate-mode drawing surface with measurable value: one control for thousands of rectangles. The current rendering package is [Microsoft.Graphics.Win2D 1.4.0](https://www.nuget.org/packages/Microsoft.Graphics.Win2D/1.4.0); see [Microsoft's Win2D overview](https://learn.microsoft.com/windows/apps/develop/win2d/).

A future `NtfsStorageScanner : IStorageScanner` should first probe filesystem, volume-handle access, supported USN record versions and cancellation. [FSCTL_ENUM_USN_DATA](https://learn.microsoft.com/windows/win32/api/winioctl/ni-winioctl-fsctl_enum_usn_data) can enumerate MFT references. [USN_RECORD_V2](https://learn.microsoft.com/windows/win32/api/winioctl/ns-winioctl-usn_record_v2) contains file/parent references, names and attributes, **not logical or allocated size**. Its variable record lengths/versions need validated parsing. USN enumeration alone therefore cannot substitute for accurate byte totals or guaranteed complete hard-link paths.

Keep the standard scanner as fallback, with the chosen strategy and reason visible. An experimental hybrid can assemble parent references and verify scope/reparse boundaries, then obtain logical lengths through directory metadata and compare complete path sets and aggregates against the standard scanner. Optional selected-file/background enrichment can use [FILE_STANDARD_INFO](https://learn.microsoft.com/windows/win32/api/winbase/ns-winbase-file_standard_info) for EndOfFile, AllocationSize and NumberOfLinks, associating native volume/file identity to avoid false deduplication. Unknown/error states must stay distinct from zero. Measuring allocation may require per-file handles and has a different performance/privacy contract from basic enumeration. Compressed/sparse data, alternate streams, cloud placeholders and links outside the scanned root require additional semantics before any recovery estimate.

Implement that experiment only after comparative tests on NTFS drives with denied access, V2/V3 records, external hard links, changing files and fallback paths. Benchmark full enumeration plus all size-enrichment work, not just USN enumeration. Never elevate automatically. Next useful improvements are incremental snapshot refresh, optional measured allocation, hierarchy boundary highlighting, localization, signed distribution and broader Windows/DPI validation.
